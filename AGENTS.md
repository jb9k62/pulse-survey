# AGENTS.md

Instructions for AI coding agents working in this repo. Read this first, every session.

## What this project is

A small, production-quality slice of a multi-tenant pulse survey SaaS.

- Full requirements: `requirements.md`.
- Task list: `TODO.md`.
- Design, trade-offs and AI workflow write-up: `SOLUTION.md`.
- Spec or plan: must be written and committed before any implementation code.

The assessor grades how the human directs and checks AI output, not only the code. Keep the human in control: propose, then act on what they approve.

## Reference source (read this before writing framework code)

The NestJS and Drizzle sources are vendored in `references/` as read-only git submodules,
pinned to the latest stable releases:

| Path | Project | Pinned at |
|---|---|---|
| `references/nest` | NestJS | commit `6739656` (tag `v12.1.0`), shallow |
| `references/drizzle-orm` | Drizzle ORM monorepo (orm, kit, zod, seed) | commit `15454db` (tag `0.45.3`), shallow |
| `references/react` | React (library source) | commit `1d34f91` (tag `v19.3.0`), shallow |
| `references/react.dev` | react.dev (documentation site) | commit `44b0b5f` (docs site version 19.3), shallow |

After a fresh clone, fetch them with `git submodule update --init --depth 1`. A fresh clone fetches
the pinned commit only, not the tag ref, so `git describe --tags` inside a submodule is not a
reliable version check. The commit recorded in the index is the pin.

Three local skills map the useful parts of that source, so you can go straight to a tested
example instead of guessing or trusting an older tutorial:

- `.pi/skills/nestjs-reference/SKILL.md` - guards, role checks, DTO validation, exception
  filters, interceptors, e2e testing, request scoping, database modules.
- `.pi/skills/drizzle-reference/SKILL.md` - pg-core schema and column types, unique
  constraints, indexes, RLS policies, selects, conflict handling, transactions, aggregate
  functions, migrations, seeding.
- `.pi/skills/react-reference/SKILL.md` - components, state, effects, forms and Actions,
  data fetching, Suspense, TypeScript, testing, the React Compiler and the rules of React.
  Its companion `docs-index.md` lists every page in the pinned react.dev checkout with its
  canonical URL and local path, generated by `npm run react:index`.

Read the relevant skill before writing code in that area. Each one lists file paths into
the submodule, notes the version gotchas that older docs get wrong, and states the project
rules that override the samples.

The submodules are reference material only. Never edit them, never import from them and
never add them to `tsconfig` paths.

## Hard constraints

- Stack: TypeScript, NestJS, PostgreSQL, React 19 (currently 19.3.0). Do not add other core frameworks without asking.
- The front end is a **client-only SPA**: React rendered entirely in the browser, talking to the
  NestJS API over HTTP. No React Server Components, no server rendering, no Server Functions, no
  framework router. Follow the client-side practices in `.pi/skills/react-reference/SKILL.md`.
- Must run locally with no external identity provider and no paid cloud service.
- Each user belongs to exactly one organisation and has one role: `Manager` or `Member`.
- **Tenant isolation is the top rule.** No query, endpoint or UI path may read or write another organisation's data. The organisation always comes from the authenticated user, never from the request body or query string.
- The current user and organisation come from a server-side session row (an opaque token in an httpOnly cookie), never from a cookie that carries a user or organisation id. See [ADR-0002](okf/adr/0002-dev-sign-in-with-server-side-sessions.md).
- The seeded user picker is a development-only affordance. It stays behind the dev flag, the flag defaults to off, and the app must refuse to start with it on in production. Never make it the production sign-in path.
- A survey has at most 3 questions. Question types: rating 1 to 5, and yes/no.
- A Member can submit one response per active week per survey. Enforce this in the database, not only in code.
- Managers can create and manage surveys only in their own organisation.
- Keep scope tight. Build the smallest end-to-end happy path first, then harden it. Do not add features that are not in `requirements.md`.

## Engineering rules

- TypeScript strict mode. No `any` unless there is a comment explaining why.
- Validate all input at the API edge.
- Every tenant-scoped feature needs a test that proves org A cannot see or change org B data.
- Test the summary maths (completion count, completion rate, rating average and count, yes/no counts) and the one-response-per-week rule.
- Run the tests and the type check before saying a task is done. Report failures honestly with the output.
- Do not invent APIs. When unsure about NestJS or Drizzle, read the pinned source in
  `references/` (start with the matching skill in `.pi/skills/`). For anything else, check
  the library's current docs.

## Git

- Small, focused commits that show how the work progressed. Never squash or rewrite history.
- Only commit when the human asks.
- Every commit message states the model used, for example `Model: Claude Opus 5.5 (claude-opus-5-5) via Claude Code`, plus the tool's co-author line.
- Never commit secrets, `.env` files or personal data.

## Every agent turn

1. Add a row to the validation log in `SOLUTION.md` (section 7): what the human asked for or steered, what they rejected or corrected, and how the output was checked. Record rejections and corrections honestly, since they are assessed.
2. Update `TODO.md`: tick finished tasks and add new ones.
3. When a design decision is made, record it in `SOLUTION.md` with the reason.

## Writing style (all docs, comments and commit messages)

- Simple, plain English.
- No em-dashes. Use commas, full stops, colons or brackets.
- South African English spelling: organisation, behaviour, colour, judgement, prioritise.
  Exception: code identifiers, library names and API fields may use US spelling where the ecosystem expects it (for example `Organization` in code is fine if you choose it, but be consistent).

## Session logs

AI session transcripts go in `ai-logs/`. Remove personal data (names, emails, home paths, tokens) before committing.
