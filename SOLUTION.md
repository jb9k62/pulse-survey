# SOLUTION.md

**Purpose:** This file explains how the solution was designed and built. It covers the design and trade-offs, known gaps and next steps, the AWS production design note, and the AI workflow, including how the agent driver (me) validated the AI's output. It is a required deliverable (see `requirements.md`, sections 2, 6, 7 and 8).

## 1. Design choices

- **"This week" definition:** a **calendar week, ISO 8601, in UTC** (Monday 00:00:00 to Sunday
  23:59:59.999). One pure server-side function, `weekStartOf(instant)` =
  `date_trunc('week', instant at time zone 'utc')::date`, is called by both submit and summary,
  the response stores it in a `week_start date not null` column, and
  `UNIQUE (survey_id, user_id, week_start)` is the rule. The client never sends the week and a
  `week_start` in a request body is ignored; the form displays the week it is answering into.
  Reasoning: the requirement lets us pick either shape, and both avoid the timezone question if
  the boundary is fixed in UTC, so the choice came down to explainability. A calendar week makes
  "this week" a phrase the UI can use literally, keeps the demo and the tests reproducible, and
  needs one `date_trunc` and one unique index. Costs recorded rather than hidden: the summary
  resets at Monday 00:00 UTC, so the seed backfills the current week, and a Member far from UTC
  has a few hours at each end of the week that fall outside their own calendar week, which is why
  the UI shows the week's dates and a per-organisation timezone is a known gap. Full record:
  [ADR-0004](okf/adr/0004-calendar-week-in-utc.md). The timezone gap is designed, not built, in
  the proposed [ADR-0009](okf/adr/0009-per-organisation-timezone-for-the-week.md).
- **Tenant isolation approach:** **database row-level security, declared in Drizzle, with the API
  connecting as a separate non-owner role**, plus application-layer scoping as a second layer.
  `pulse_owner` owns the schema and runs migrations and seed data; `pulse_app` holds only the DML
  grants the API needs and is what the app connects as. Because the app role owns no table, the
  owner exemption never applies to it and no `FORCE ROW LEVEL SECURITY` statement is needed. One
  transaction per request sets `app.current_org`, `app.current_user`, `app.current_role` and
  `app.current_session_token` with `set_config(name, value, true)`, and every query runs on that
  transaction handle. Policies are one org-isolation read predicate per tenant table, with
  survey and question writes also needing the Manager role (migration 0006), plus a read and an
  insert policy on `responses` and `answers`: a Member reads only their own rows, a Manager reads
  the organisation's, and nobody inserts a response for someone else (migration 0005). Two queries run before a tenant context exists and get
  named exceptions rather than open policies: the session lookup (a policy on `sessions` matching
  the token hash set for that transaction, so the table cannot be listed) and the dev user
  directory (a `SECURITY DEFINER` function in a `dev` schema, called only when the dev flag is
  on). Reasoning: the brief asked for row-level security and for both cross-organisation and
  cross-member protection, and the research note showed that RLS alone is decoration when the
  application connects as the table owner. The non-owner role is the production answer, it leaves
  the seed and `pg_dump` running as the owner where bypassing policies is what you want, and it
  makes the isolation test honest, because the test connects as `pulse_app` and a wrong policy
  then fails the test instead of passing quietly. Costs: two connection strings, a grant step in
  the migration path, a transaction per request, and the rule that a query escaping to the pool
  runs with no settings and sees no rows at all (safe, but a silent bug), which the repository
  shape has to make hard to write. `push` is not used
  against this database, because drizzle-kit can disable RLS it does not know about. Full record:
  [ADR-0005](okf/adr/0005-rls-with-a-non-owner-app-role.md).
- **Tenant plumbing (auth guard, request transaction, dev gate):** one global `DbModule` owns
  `APP_CONFIG`, the `pulse_app` pool and the Drizzle instance, so the guards, the interceptor and
  the controllers inject a token instead of importing a module. The auth guard resolves the
  session in its own transaction (it must: guards run before interceptors, so the request
  transaction does not exist yet), reading session then user then organisation in the order the
  policies require, and deleting an expired or deactivated row in that transaction and returning
  `null` so the delete commits. The interceptor then opens exactly one request transaction per
  request, public routes included, sets all four `app.current_*` values (using `''` for absent
  values, because `nullif(..., '')` fails the policies closed) and puts the handle on the request
  for `@CurrentTx()`. The dev gate is `@DevOnly()` read by the auth guard, which throws
  `NotFoundException` when `AUTH_MODE=off`; because guards run before pipes, a disabled dev route
  is a 404 even for an invalid body, and no second guard class is needed. The cookie name
  `pulse_session` lives once in `sessions.service.ts`; nothing else hardcodes it. `@CurrentUser()`
  returns `Principal | null` rather than throwing when absent, because `GET /api/me` is public and
  must answer a signed-out state; the protected routes cannot see `null` because the guard has
  already answered 401.
- **Data model:** `organisations`, `users` (one organisation, one role, `joined_at` and a nullable
  `deactivated_at`), `sessions` (a hash of the token, never the token), `surveys`,
  `questions` and `responses`, with `answers` carrying the typed values. Three details carry the
  rules: the three-question limit is `position smallint` with `CHECK (position between 1 and 3)`
  and `UNIQUE (survey_id, position)`, so a fourth question is unrepresentable rather than
  counted; an answer holds exactly one of `rating_value` (1 to 5) or `yes_no_value`, enforced by
  `CHECK (num_nonnulls(rating_value, yes_no_value) = 1)`, so a blank or double answer cannot be
  stored; and composite foreign keys keep an answer with the survey it belongs to
  (`answers(survey_id, question_id)` to `questions(survey_id, id)` and `answers(survey_id,
  response_id)` to `responses(survey_id, id)`), so answers cannot be crossed between surveys.
  Submit is all or nothing with one answer per question; drafts are out of scope.
- **How surveys are created:** a **Manager-only `POST /surveys` endpoint plus seeded surveys**, one
  active survey per organisation with three questions. The React app keeps the two flows the
  requirements name and gains no create screen. Reasoning: requirement 4.2.3 allows any of seed
  data, fixtures, an admin endpoint or a CLI, but 4.1.4 says a Manager can create and manage
  surveys, so the rule needs an endpoint to be demonstrated and tested rather than only a seed
  row. Leaving the form out keeps the UI minimal, which section 5.3.2 asks for. The list endpoint
  returns every survey of the organisation, archived included, newest first, and only the
  active-survey lookup filters on `status`, so the Manager screen can select an archived survey to
  read its summary (contract section 5 ruling 5, 2026-09-26).
- **Current user and organisation identification:** a **credential-less dev sign-in** backed by a
  **server-side session**. The React app lists the seeded users across all organisations and the
  visitor becomes whichever one they pick, until they log out. A random opaque token sits in an
  httpOnly cookie and is matched to a `sessions` row; the organisation and role are read from that
  row's user, never from the request. The picker and the dev session route are gated behind a
  development flag that defaults to off, and the app refuses to start with the flag on in
  production. Reasoning: the requirements name a token, a session or a header (section 4.2.2) and
  allow picking a seeded user (section 5.3.3), so a session cookie is the shape the requirements
  already permit. It beats a header because the tenant is then derived server-side from a revocable
  row, where a header lets the client assert it, which is the rule this project exists to keep. It
  also gives real logout and revocation, which a signed stateless cookie cannot. Two corrections to
  the original proposal are recorded in the ADR: "auth-less" is the wrong name (there is
  authentication and a session, only the credential is missing), and the picker needs the dev gate,
  since section 5.3.3 permits a demo sign-in rather than a permanent way to become anyone. The one
  honest risk, recorded there rather than hidden, is that listing users across organisations is a
  cross-tenant disclosure which a strict reading of section 2.6 could call a breach; the defence is
  that the rule guards organisation data, the directory is the seeded sign-in affordance the
  requirements allow, and outside development the route does not exist. Full record:
  [ADR-0002](okf/adr/0002-dev-sign-in-with-server-side-sessions.md).
- **Local database:** PostgreSQL in **Docker Compose**, on the official image pinned to
  **`postgres:18.6`**, the current stable release (18 is the supported major until 2030; 19 is still
  in beta). One `db` service with a named volume, a `pg_isready` health check so
  `docker compose up --wait` returns only when the server is ready, and the port bound to
  `127.0.0.1`. Only the database runs in Compose; the API and the React app run on the host.
  Reasoning: one command gives every reviewer and every test run the same server, which section 5.1
  asks for, with no local install and no paid service. The tag is pinned to the minor so a change
  of server shows in the diff; the Debian image is chosen over Alpine because its collation
  behaviour matches managed PostgreSQL. One trap is recorded in the ADR: from version 18 the image
  keeps data under `/var/lib/postgresql/18/docker`, so the volume must mount at
  `/var/lib/postgresql`, and the `/var/lib/postgresql/data` path most tutorials show would not
  persist anything. Full record: [ADR-0003](okf/adr/0003-local-postgres-with-docker-compose.md).
- **Front end stack:** React 19, pinned to the current release **19.3.0**, built with Vite
  (`npm create vite@latest my-app -- --template react-ts`). TypeScript strict mode, `@types/react` and
  `@types/react-dom` as dev dependencies. A **client-only SPA**: rendered entirely in the browser,
  talking to the NestJS API over HTTP, with no React Server Components, no server rendering, no
  Server Functions and no framework router. No routing or data-fetching library either: the slice
  has two screens and one API, so React's own state and `fetch` are enough. Reasoning: React 19 is
  the current major, the docs recommend Vite for a client-only SPA that does not need a framework,
  and the requirements ask for a very small UI to exercise the API rather than a product shell.
  Adding a framework, a query library or a server rendering path would be scope the requirements do
  not ask for, and RSC in particular needs a bundler and framework runtime this slice does not
  have. The client-side practices the app follows are listed in
  `.pi/skills/react-reference/SKILL.md`.
- **Project layout:** one **npm workspace** at the repository root, holding `apps/api` (NestJS) and
  `apps/web` (Vite + React 19) as workspaces with a single root `package-lock.json`. The root
  `package.json` keeps the documentation tooling and gains delegating scripts (`dev:api`,
  `dev:web`, `build`, `test`, `test:e2e`, `lint`, `typecheck`). Reasoning: the two apps are always
  run together, so one install and one lockfile keeps them in step, and a delegating script gives
  the reviewer one command per task without adding a task runner or a monorepo tool. Cost: npm
  hoisting can place a package that one workspace relies on indirectly into the other workspace's
  `node_modules`, so each workspace has to declare what it imports even where a CLI scaffold
  assumed a hoist. That bit us once with `vite` (section 7, row 17).
- **Scaffolding:** both apps are CLI output, then adjusted. The API came from the **NestJS 12.0.7
  CLI** (`new api --package-manager npm --skip-git --skip-install --strict`), the web app from
  **`create-vite` 9.2.1** with the `react-ts` template. Worth knowing about the current NestJS
  CLI: it scaffolds an **ESM** project (`"type": "module"`, `module: nodenext`), **oxlint**
  instead of ESLint, and **Vitest** instead of Jest, so both apps now share one test runner and one
  linter by default. Every deviation from raw CLI output, and why, is listed in section 7, row 17.
- **The spec, and how it is split:** the plan of record is
  [`okf/design/spec.md`](okf/design/spec.md): 917 words covering what to build, the build order, the
  rules that must hold, the definition of done and the two open decisions. The contracts an
  implementer must not invent live in four concepts beside it, linked from the spec and the bundle
  index: [data model](okf/pulse-surveys/domain-model.md), [tenant isolation and test plan](okf/pulse-surveys/architecture.md),
  [API surface](okf/pulse-surveys/api.md) and [front end](okf/pulse-surveys/frontend.md). Reasoning:
  requirement 7.3 asks for a short spec committed before the code, and the first draft came back at
  5,966 words, which is a design document rather than a brief plan. The sections were moved verbatim
  rather than rewritten, so the reviewed content is unchanged, and the reasoning stays where it
  belongs in the ADRs and design notes. A reader who wants only the plan reads one page; an
  implementer follows four links.
* **API-edge validation:** **Zod 4** schemas run by Nest's built-in
  `StandardSchemaValidationPipe`, registered once as an `APP_PIPE` provider, with the schema attached
  per parameter (`@Body({ schema })`, `@Query({ schema })`). One schema language covers the request
  DTOs, the query parameters and the environment config, and the TypeScript type is inferred from the
  schema with `z.infer`, so the type and the runtime check cannot drift. Unknown keys are stripped,
  which is what makes "an `organisationId` in the body is never read" structural rather than a
  promise. Reasoning: `AGENTS.md` requires validation at the API edge and the rules are specific
  (1 to 3 questions, `rating` or `yes_no`, a rating of 1 to 5, one answer per question matching its
  type, an optional Monday for `weekStart`), so the shape has to be declared somewhere; a schema is
  also the type, and the pipe ships in `@nestjs/common` at the pinned version, so there is no custom
  pipe to maintain and no decorator metadata to keep in step. Costs: a new runtime dependency in
  `apps/api`, a newer pipe with less community material behind it, and the trap that a handler which
  forgets `@Body({ schema })` silently skips validation, which the `CHECK` constraints and the e2e
  tests contain. Full record: [ADR-0006](okf/adr/0006-zod-at-the-api-edge.md).
- **Where the design lives:** in [`okf/`](okf/index.md), an Open Knowledge Format v0.2 bundle
  (one concept per markdown file). This file stays the short summary and links into it. It holds
  the overview, the plan of record and its four contract concepts, ADR-0001 to ADR-0008, the
  design notes, the two guided tours and the demo script. Run `npm run okf:view` to browse it.
  Reasoning: [ADR-0001](okf/adr/0001-keep-design-in-okf-bundle.md).
- **How a concept is marked as reviewed:** a `verified` frontmatter entry naming the person and the
  date, `{ by: "human:Jordan Hunt", at: 2026-09-26 }`. The viewer derives a trust tier from it
  (`unverified`, `machine-confirmed` or `human-reviewed`), and that tier is only honest while the
  text is unchanged, so a concept whose content moves needs re-verifying. The six substantive
  concepts carried the entry. `okf/adr/template.md` and `okf/adr/readme.md` deliberately do not,
  because the template would then stamp a review onto every ADR copied out of it. Reasoning: the
  brief asks for the AI workflow to be inspectable, and a dated human entry is the difference
  between "a model wrote this" and "a person read it". When a concept's text changes, the entry
  comes off again: the overview and both design notes lost theirs on 2026-09-26, when the week and
  isolation decisions were written into them, and ADR-0002 lost its entry on 2026-09-27 (row 56)
  for the same reason. The bundle now reads two `human-reviewed` concepts (ADR-0001 and ADR-0003),
  and the rest need reading before an entry is added or returns.
- **Where framework reference material lives:** the NestJS, Drizzle, React and react.dev sources
  are vendored as read-only, shallow git submodules under `references/`, pinned by commit
  (`references/nest` at `v12.1.0`, `references/drizzle-orm` at `0.45.3`, `references/react` at
  `v19.3.0`, `references/react.dev` at docs site version 19.3). Three small skills in
  `.pi/skills/` map the useful parts of that source, and `AGENTS.md` points at them. Reasoning: an
  agent that reads the exact pinned source cannot invent an API or copy a pattern from an older
  version, and the paths stay reviewable in the diff. Cost: a clone needs one extra
  `git submodule update --init --depth 1` step and about 130 MB of reference checkouts, and the
  skills need re-checking when we move tags. The React skill carries a generated page index
  (`docs-index.md`) so an agent can point at a real page instead of a remembered one; it is
  regenerated with `npm run react:index`.
- **Response submission and the weekly summary:** `POST /api/surveys/:id/responses` (Member) and
  `GET /api/surveys/:id/summary` (Manager). Submit runs entirely on the request transaction, so it
  is all or nothing: it looks the survey up scoped to the session organisation (404, never 403),
  rejects an archived survey with 409, checks the answer set against the survey's questions (400,
  including a duplicated `questionId`, which would otherwise reach the unique constraint as a 500),
  takes the week from the database clock through `currentWeekStart`, and inserts the response with
  `onConflictDoNothing` on the (survey, member, week) unique constraint so a duplicate week becomes
  409 rather than 500. The body never supplies the organisation, user, week or question ids. The
  summary defaults `weekStart` to the current week, accepts an archived survey with 200, and
  reports completion against an eligible denominator of the Members whose membership overlaps the
  week, a half-open UTC window (`joined_at < week_start + 7 days` and not deactivated before the
  week started). The rate is a fraction and is not clamped; a zero-eligible week is `null` and a
  zero-response question is `null` average with count 0 (or yes/no 0), never `NaN`. All of the
  counting and dividing lives in `src/surveys/summary.math.ts` alone, which a test enforces by
  walking the source with the TypeScript compiler API.
- **Front end session state and the five screen states:** `src/session/SessionProvider.tsx` is the
  only Context and the only place that calls `GET /api/me`, with the ignore cleanup StrictMode
  needs, and `App` derives the five screen states in render from it (bootstrap loading, bootstrap
  failure, signed out with the picker, signed out with sign-in disabled, Member, Manager).
  Domain-driven decisions recorded here: (1) `SessionState` is a discriminated union
  (`SignedInSession | SignedOutSession`) exactly as contract 2.4 writes it, so `App` narrows
  instead of asserting non-null, and a third bootstrap sub-state, `failed`, shows a `/api/me`
  failure honestly rather than pretending sign-in is disabled. (2) The API client never throws:
  `src/api/parsers.ts` validates a payload once and throws on a bad shape, `client.ts` catches a
  parser throw or a rejected fetch and returns `ApiResult` with a `Failure` of kind `http`,
  `network` or `malformed`, and the form action returns its outcome as a value. A throw inside the
  action would cancel the `useActionState` queue and reach the `ErrorBoundary`, so it must not
  happen. (3) The submit outcome maps by status: `ok` becomes `submitted` with the week label the
  server returned, `409` becomes the pinned duplicate sentence next to the form, `400` becomes
  `invalid` with the API message, and every other failure becomes `error` with the API message or
  `Could not submit your answers. Try again.`. The form stays enabled when the Member has already
  answered; only the in-flight submit disables the button, through `useFormStatus` inside the form.
  (4) There is no router, no data library, no shared types package and no `use client` or
  `use server`: the Vite proxy makes every call same-origin, and the question id is the `FormData`
  input name so the answers are built from the survey the server returned.
- **The Manager summary flow (React):** `ManagerScreen` loads the survey list, the Manager selects a
  row, and `SummaryPanel` renders the summary as pure presentational markup. Four front-end decisions
  are recorded here, matching the plan's decisions list for this slice. (1) `getSummary` takes a
  **required** `weekStart` and the screen always passes the selected list item's `weekStart`, per
  contract section 5 ruling 2: the field exists so the Manager screen can pass the week it is
  showing, so it is never omitted and the client never computes a week. (2) The percentage comes from
  `Intl.NumberFormat('en-ZA', { style: 'percent', maximumFractionDigits: 0 })`, never from
  `rate * 100` or `completed / eligible`, so no arithmetic divides in the client; a test pins
  `completed: 2, eligible: 3, rate: 0.5` to `50%`, which the server's rate decides rather than the
  counts. (3) The null and the non-finite cases are kept apart: a `null` rate renders
  "no eligible members", a non-finite rate renders **no rate element at all**, and a `null` or
  non-finite average renders "no answers yet", so a rejected payload can never become a false
  statement or the text `NaN`. The parser rejects a non-finite number first and `SummaryPanel`
  guards again at render, as defence in depth. (4) `ManagerScreen` returns one
  `<section className="card">`, not a `<main>`, because `SignedInShell` already owns the page's
  `<main>`; it stores the selected survey id and derives the item in render rather than storing the
  object, it does not read `useSession` (so it stays standalone-testable), and both data loads are
  Effects with an `ignore` cleanup because StrictMode double-invokes effects. The list reuses the
  existing `.picker`, `.button`, `.badge`, `.summary` and `.week` classes, so `app.css` is unchanged.
- **Dev sign-in is enforced in the database, not only by the flag (row 41):** migrations run in
  every environment, so they no longer let `pulse_app` call `dev.list_users()` or
  `dev.create_session()`: `0004` revokes what `0002` granted, and `grantDevSignIn()` (run only by
  `npm run db:seed` when `AUTH_MODE=dev`, and by the test setup) grants them back; the seed
  revokes them when `AUTH_MODE=off` and refuses to run outside development (row 56). At startup
  the API checks that the grants match `AUTH_MODE` both ways and refuses to start otherwise. Reason: the review showed a
  plain `pulse_app` connection could list every organisation's users and create a Manager session,
  so one SQL injection or a leaked app password would have been a cross-tenant takeover whatever
  the flag said. Cost: after changing `AUTH_MODE`, re-run `npm run db:seed` so the grants follow.
- **`NODE_ENV` fails closed (row 41):** only `development` and `test` count as development. Any
  other value, or none, is production: `AUTH_MODE=dev` is refused and the cookie is `secure`.
  Reason: the old rule refused only the exact value `production`, so a container that forgot
  `NODE_ENV` would have allowed the picker and sent the cookie without `secure`. `dev:api` and the
  Playwright config set `NODE_ENV=development`, and Vitest sets `test`.
- **Every respondent is eligible (row 41):** the summary's `eligible` counts active Members in the
  week plus anyone who responded to the survey that week. Reason: `role` is today's role, so a
  respondent later promoted to Manager would count as completed but not eligible and push the rate
  above 1. Counting respondents makes `completed <= eligible` true by construction, which is better
  than a clamp that would hide the mismatch. The seeded numbers do not change.
- **UI restyle, retro look (row 42):** light and dark themes switched by one toggle in a shared top
  bar, stored in `localStorage` and set on `<html data-theme>` by an inline script before the
  first paint, so there is no flash of the wrong theme. The system preference is the default until
  the user picks one. Fonts are VT323 (headings, brand, big numbers) and IBM Plex Mono (body and
  controls), **self-hosted** through `@fontsource/*` and bundled by Vite as WOFF2. Reason: the app
  must run with no external service, browsers now partition their caches so a font CDN gives no
  shared-cache benefit, and a third-party font request sends each visitor's IP to that provider.
  Layout: the Manager sees the survey list and the summary side by side (stacked on a phone), the
  Member answers numbered question cards with key-style choices, and the picker groups users by
  organisation in two columns. The summary bars size their segments with `flex-grow` from the
  server's numbers, so the client still never divides. No CSS framework was added.
- **One shared contracts package (row 44):** every request and response shape is a Zod schema in
  `packages/contracts` (`@pulse/contracts`). The API validates with it and types its responses from
  it; the web app parses every response with it. Reason: the hand-mirrored web types and parsers
  could drift from the API without any check failing. The human chose this over keeping the copies
  (my recommendation) or Zod on the web only. Node loads the built `dist/`, Vite and the web `tsc`
  read `src/` through a `source` export condition.
  [ADR-0008](okf/adr/0008-shared-contracts-package.md).
- **Nest feature modules (row 44):** `SurveysModule`, `DevModule`, a global `ConfigModule`, and
  `SessionsController` in `AuthModule`; the global guards, pipe, interceptor and filter stay in
  `AppModule`. Reason: the `nestjs-reference` samples give each feature its own module, and one flat
  `AppModule` hid which providers belong together.
- **Database errors mapped where they are raised (row 44):** the exception filter no longer knows
  any constraint names. The surveys service catches the one-active-survey `23505` and throws `409`.
  Reason: the filter held survey rules, and its duplicate-week mapping was dead code, since
  `ON CONFLICT DO NOTHING` already turns that case into a `409` in the service.
- **One fetch hook (row 44):** `useApiResult({ key, load })` replaces four hand-written copies of the
  Effect, `ignore` flag and loading state. The loading state is derived by comparing keys, not set.
  Reason: the react.dev custom-Hook pattern, and ManagerScreen no longer needs to set its loading
  state from the click handler.
- **Interactive widgets in the OKF viewer (row 51):** `packages/okf-widgets` is a React 19.3
  bundle built by Vite in library mode and inlined into `viz.html`, and a `widget` fenced block
  mounts one widget in a concept. The widgets import the app's own pure code (`summary.math.ts`,
  `weekOf`, `summarySchema`, `SummaryPanel`) through Vite aliases, and the parts that are SQL in
  the app (the week start, the RLS predicate, the eligible count) are labelled models pinned by
  tests to the real code's cases. Reason: Geoffrey Litt's "Understanding is the new bottleneck"
  asks for interactive figures alongside the explainer and quiz, and a widget that ran a copy of
  the maths could drift from the app without any check failing. The human chose the package
  over React from a CDN. This is documentation tooling: nothing in `apps/` changed.

## 2. Trade-offs

The decisions are in section 1 and the ADRs. These are the costs I accepted with them, and why.

- **Row-level security over application scoping alone.** It is more machinery: two database
  roles, a transaction per request, four transaction-local settings, a second short transaction
  in the auth guard (guards run before interceptors), and a startup check that the app role can
  bypass nothing. In return a forgotten `where` clause returns nothing instead of another
  organisation's rows, and the isolation tests connect as `pulse_app`, so a wrong policy fails a
  test instead of passing quietly. Application scoping stays as the second layer.
- **A calendar week in UTC over a rolling window.** "This week" means the same thing in the UI,
  the database and the tests, and one unique index enforces the rule. The cost is that an
  organisation far from UTC has a few hours at each end of its week that fall into the next or
  previous UTC week. A per-organisation timezone is the fix (section 3).
- **A dev-only user picker over a real sign-in.** The demo needs no identity provider, which the
  brief rules out, and the session layer behind it is production-shaped (opaque token, hashed at
  rest, revocable). The cost is that a deployed build has no way in until a real sign-in replaces
  the two dev routes ([ADR-0007](okf/adr/0007-no-production-sign-in.md)).
- **Surveys created through the API and the seed, with no create screen.** It proves the Manager
  rule with tests and keeps the UI to the flows the brief names. The cost is that a person trying
  the app cannot create a survey without a tool like `curl`.
- **An honest completion rate.** Eligible means Members whose membership overlaps the week, plus
  anyone who responded. The SQL is harder to read than "count the Members", and the summary makes
  six small queries rather than one. At this scale clarity wins; with real data it becomes one
  query or a weekly rollup (section 4).
- **One shared contracts package.** The API and the web app cannot drift apart, because both parse
  with the same Zod schemas. The cost is a build step: Node loads the built `dist/`, so the dev
  script runs a contracts watcher next to `nest start --watch`, and Nest also watches the
  contracts' built JavaScript as an asset, so a change to runtime behaviour alone (a `.max()`
  limit) restarts the API as well as a change to the types. It is a small shell script because
  stopping two watchers and the app they start cleanly took three separate fixes (row 57).
- **Fixed questions and no drafts.** A survey is created and archived, never edited, and a submit
  is all or nothing. That keeps every stored response comparable within a survey, at the cost of
  survey versioning and partial answers.
- **Heavy design records for a four-hour brief.** The OKF bundle, eight ADRs, two guided tours and
  a per-turn validation log took real time away from the product. I chose that because the
  brief puts weight on how the AI was directed and checked, and the records are what make that
  inspectable. A lighter version would keep the ADRs and the log and drop the tours.
- **Cheap models for generation, maximum thinking for review.** The pi workflows run DeepSeek V4.1
  Flash throughout, at low thinking to implement and max to design and review, after a
  three-model eval (rows 20 to 22). The saving is real; the cost is that every review finding has
  to be confirmed by hand before it is acted on, which the log records.

## 3. Known gaps

Each of these is a real limitation, recorded rather than hidden. The first four are deliberate scope
cuts, the last is a consequence of a decision.

- **No per-organisation timezone.** A week is UTC ([ADR-0004](okf/adr/0004-calendar-week-in-utc.md)),
  so an organisation whose local week differs from UTC has a few hours at each end of the week that
  fall outside its own calendar week. The UI shows the week's dates to reduce the surprise. The fix
  is a timezone column plus daylight saving handling.
- **No production sign-in.** The session layer is production-shaped, but the only way to obtain a
  session is the dev-only picker, so the deployed application has no way in. This is a recorded
  decision, not an oversight: an OIDC provider would replace the two dev routes and leave the rest
  alone, and a password flow would add storage, reset, rate limiting and lockout work that no
  requirement asks for. [ADR-0007](okf/adr/0007-no-production-sign-in.md).
- **No survey editing.** A survey can be created and archived, not edited, and its questions are
  fixed once responses exist. Survey versioning is the real fix.
- **No drafts.** Submit is all or nothing, so a Member who answers half a survey and closes the tab
  starts again. Acceptable for three questions, wrong for thirty.
- **The completion rate is not clamped.** A rate above 1 would be a bug in the denominator, and
  clamping would hide it, so the code returns the honest number. Every respondent is counted as
  eligible, so the rate cannot exceed 1 even when a respondent's role changes later, and
  `test/summary-eligibility.spec.ts` asserts it.

## 5. Production readiness on AWS (design note)

This is the design-only answer to requirement 6, and it invents nothing the repository does not
have. The same note also lives in the design bundle at
[okf/design/aws-production-note.md](okf/design/aws-production-note.md).

### 5.1 Deployment

The API image is built from `npm run build` and runs `node dist/main`, pushed to ECR (Elastic Container Registry, AWS's private image
store) and run on ECS (Elastic Container Service) Fargate, which runs containers without servers to
manage, behind an Application Load Balancer (ALB). App Runner, a simpler managed container service,
is the cheaper alternative when there is no need for an ALB. The database is RDS (Relational Database
Service, managed PostgreSQL) in private subnets with TLS (Transport Layer Security, encryption in
transit) required. The two
roles are created the way `apps/api/db/bootstrap.sql` does it, and the app role is never
`rds_superuser` and never has `BYPASSRLS`, which is exactly the invariant the API asserts on every
boot. Migrations run as a separate one-off task using `drizzle-kit migrate` and
`DATABASE_URL_OWNER`, before the new API revision is rolled out; `drizzle-kit push` stays banned.

The front end needs no server because there is no server rendering. It goes to a private S3 (Simple Storage Service,
AWS object storage) bucket served by CloudFront (AWS's CDN, or content delivery network) with Origin
Access Control (OAC), which lets only CloudFront read the bucket.

One origin matters. CloudFront's default behaviour points at S3, and `/api/*` points at the ALB,
forwarding the `Cookie` header and caching nothing on that behaviour. That keeps the same-origin
property the Vite proxy gives locally: a first-party cookie, no CORS (Cross-Origin Resource Sharing, the
browser rules for calls to another domain), no `SameSite=None`. Two
hostnames would force the CORS work and the cross-site cookie work, which is why they are not the
default.

Sessions are database rows. Any task can validate any session, so there are no sticky sessions:
scale the tasks out and any of them can answer. This is a direct consequence of
[ADR-0002](okf/adr/0002-dev-sign-in-with-server-side-sessions.md) and worth naming.

### 5.2 Organisation logo storage and serving

The goal is that the backend carries no image bandwidth and no image cost, while access stays
secure. Store the object key, not a URL: a `logo_key` column on `organisations` in a new migration,
with a policy and a grant like every other table. None of this exists yet.

The bucket is private, with Block Public Access on and server-side encryption, either
SSE-S3 (keys managed by S3) or SSE-KMS (keys managed in KMS, the Key Management Service). Keys are
`organisations/<org-id>/logo/<sha256>.<ext>`, so the name changes with the content (cache busting)
and one organisation's objects group for lifecycle rules.

The API is the only writer, so validation cannot be bypassed. A Manager-only route validates the
content type and size, re-encodes or at least strips EXIF (photo metadata such as camera
and location), caps the dimensions, rejects SVG (an image format that can carry script), takes
the organisation id from the session and never from the body, then writes the key. This follows the
[tenant isolation](okf/pulse-surveys/architecture.md) rule that the organisation always comes from the
session.

Serving never streams the image through the API and never presigns on every page load. CloudFront
with OAC serves the bytes; the API only mints a short-lived signed URL (minutes) for the
organisation's own key and returns small JSON. CloudFront and S3 carry the bytes and the cost, the
ALB and the API task never see them, and because the object is immutable it caches for a long time.
The bucket stays private, the TTL (time to live, how long the URL works) stays short, signed URLs are not logged, and the key is derived
from the session, so one organisation can never be handed another's key. If a logo really must be
public, it gets a separate public prefix, never the private objects.

One honest tenancy sentence: S3 has no row-level security, so the signing route and the key layout
are the only things standing between two organisations' logos.

### 5.3 Tenancy, security and scaling priorities

1. Keep the app role non-owner and non-`BYPASSRLS`, and assert it on the real RDS instance, not only
   at boot.
2. Keep the tenant context transaction-local. That is what makes a transaction-pooling proxy (RDS
   Proxy or PgBouncer, which share a few database connections between many requests) safe.
3. Every new table needs its policy and its grant in the same migration. A missing policy fails
   closed; a missing grant fails at runtime.
4. The organisation still comes only from the session, including the logo upload and signing routes.
5. Production sign-in is the gap. `AUTH_MODE` stays `off` in production, and `AUTH_MODE=dev` with
   `NODE_ENV=production` is a startup failure. The first production step is an identity provider
   (Cognito, AWS's user sign-in service, or any OIDC provider, where OIDC is OpenID Connect, the
   standard sign-in protocol) replacing the two dev routes, keeping the `sessions` table and the
   guard. The dev picker must never be switched on to make a deployed demo work
   ([ADR-0007](okf/adr/0007-no-production-sign-in.md)).
6. Revoke `EXECUTE` on `dev.list_users()` and `dev.create_session()` when the flag is off. It is
   unconditional today and is an open TODO.
7. TLS at every hop, secrets in Secrets Manager or SSM (Systems Manager)
   Parameter Store, and a short session TTL.
8. Least-privilege IAM (Identity and Access Management) permissions per task, with S3 write only under the logo prefix.
9. WAF (Web Application Firewall) in front of CloudFront, rate limits on the sign-in and logo routes, and no personal data in
   logs.
10. Scaling: the API is stateless, so start at two tasks for availability. The database is the first
    bottleneck, and the hot paths already have indexes (`sessions_token_hash_key`,
    `responses_survey_week_idx`, `responses_org_week_idx`).
11. Read replicas only when a read path needs one, and remember a replica is another place the
    tenant context must be set. Weekly summaries are bounded aggregates, so a nightly rollup beats a
    wider index.
12. Static assets and logos never touch the API, which is the biggest cost lever.
